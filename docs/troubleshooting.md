# Troubleshooting Notes

## SSH Connection Timed Out

### Symptom

The EC2 instance was running and the security group permitted SSH, but the connection timed out.

### Investigation

The instance configuration was checked first, followed by the security group, subnet route table, and VPC internet gateway. The VPC did not have a complete route to the internet.

### Resolution

An internet gateway was attached to the VPC and the required default route was verified. Connectivity was tested again only after confirming the complete path.

### Lesson

A public IP alone does not provide internet access. The instance, security group, internet gateway, and route table must all be configured correctly.

## Private Key Was No Longer Available

### Symptom

The private key created in AWS CloudShell was lost after the temporary environment reset.

### Investigation

AWS does not allow previously generated private key material to be downloaded again.

### Resolution

The inaccessible test instance and orphaned key pair were replaced, and the environment was rebuilt with a newly generated key.

### Lesson

CloudShell should not be treated as durable storage. Private keys must be stored securely when they are created and must never be committed to GitHub.

## Nginx Returned 404 After Permissions Were Tightened

### Symptom

Both sites returned 404 responses after ownership and permissions were changed.

### Investigation

The Nginx error log reported `Permission denied` while attempting to access the site files. The Nginx account had been added to the `webdev` group, but the existing worker processes had started before that membership was added.

### Resolution

Nginx was restarted so that the new worker processes inherited the updated group membership:

```bash
sudo systemctl restart nginx
```

### Lesson

`reload` re-reads service configuration, but it does not refresh the operating-system credentials of an existing process. A restart is required after changing the service account's group membership.

## Nginx Configuration Needed Validation

### Symptom

A server-block or error-page change needed to be applied without introducing an outage.

### Resolution

The configuration was tested before reload:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### Lesson

Validate configuration syntax before asking a running service to apply a change.

## Fail2Ban Did Not Count Test Failures

### Symptom

The SSH jail was enabled, but controlled failed-key attempts were not increasing the failure count.

### Investigation

The raw SSH journal showed connection-reset events instead of the authentication-failure pattern expected by the default Fail2Ban filter mode.

### Resolution

The SSH jail was changed to `mode = aggressive`, Fail2Ban was restarted, and controlled test attempts were repeated. Detection, banning, and unbanning were then validated.

### Lesson

A security service reporting a running state does not prove that it recognizes the events generated by a particular operating-system and OpenSSH combination. Detection must be tested against the actual logs.

## SSH Hardening Could Have Caused Lockout

### Risk

Disabling password authentication or direct root login can make a remote system inaccessible if key-based access is not working.

### Validation

The SSH configuration was checked before restart:

```bash
sudo sshd -t
sudo systemctl restart sshd
```

A second independent session was opened successfully before the original administrative session was closed.

### Lesson

Never close the only working remote session until the hardened configuration has been validated through another connection.

## Health Check Reported HTTP 000

### Symptom

After Nginx was deliberately stopped, the site checks returned HTTP `000`.

### Investigation

HTTP `000` indicated that `curl` did not receive an HTTP response because the service was unavailable.

### Resolution

Nginx was restarted, the health check was run again, and both sites returned HTTP `200`. The script returned exit code `0` after recovery.

### Lesson

Testing both healthy and unhealthy states verifies that monitoring detects an actual service failure rather than always reporting success.
